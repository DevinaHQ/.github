# DOC-003 — Document Writing Standard

## Status

Approved

---

# Purpose

This document defines the official writing standard for all DevinaOS documentation.

It establishes consistent writing principles, language conventions, terminology, formatting rules, and authoring practices to ensure clarity, readability, governance, interoperability, AI compatibility, and long-term maintainability across the DevinaOS documentation ecosystem.

This standard complements DOC-001 — Documentation Metadata Standard and DOC-002 — Document Structure Standard by defining how document content shall be written.

---

# Scope

This standard applies to every official DevinaOS document, including but not limited to:

- Documentation (DOC)
- Philosophy (PHIL)
- Architecture (ARCH)
- Blueprint (BLUE)
- Information Map (MAP)
- Domain (DOMAIN)
- Capability (CAP)
- Module (MOD)
- Data (DATA)
- Artificial Intelligence (AI)
- Standards
- Specifications
- Guidelines
- Policies
- Procedures
- References
- Catalogues
- Future official documentation

This standard governs writing practices only. It does not define metadata, document structure, lifecycle, versioning, naming, or document relationships, which are governed by their respective standards.

---

# Background

As the DevinaOS documentation ecosystem continues to expand, consistency in writing becomes essential for effective communication, governance, collaboration, knowledge preservation, AI-assisted processing, and future automation.

A unified writing standard ensures that every official document presents information in a clear, predictable, professional, and platform-independent manner regardless of its author.

---

# Writing Principles

Every official document shall comply with the following principles.

- Clarity
- Simplicity
- Consistency
- Precision
- Readability
- Traceability
- Professionalism
- Platform Independence
- AI Readability
- Long-Term Maintainability

---

# Language Standard

Official DevinaOS documentation shall use:

- English as the primary documentation language.
- Formal professional writing.
- Objective language.
- Neutral tone.
- Active voice whenever practical.
- Present tense unless historical context requires otherwise.
- Consistent terminology throughout the documentation ecosystem.

---

# Normative Language

Normative statements shall use the following terminology.

| Term | Meaning |
| --- | --- |
| Shall | Mandatory requirement |
| Shall Not | Mandatory prohibition |
| Should | Strong recommendation |
| Should Not | Recommendation against |
| May | Optional permission |
| Can | Capability or possibility |

Normative language shall be used consistently throughout official documentation.

Mandatory requirements shall use **Shall**, while explanatory or informative statements should avoid normative terminology unless intentional.

---

# Writing Style

Documentation shall:

- Write concise paragraphs.
- Explain concepts before implementation details.
- Avoid unnecessary repetition.
- Use descriptive headings.
- Prefer structured lists over long narrative text.
- Use tables when they improve readability.
- Keep one primary idea per paragraph whenever practical.
- Avoid ambiguous or subjective language.

---

# Governance Writing Rules

Official governance documents shall:

- State requirements explicitly.
- Separate mandatory requirements from explanatory information.
- Distinguish informative examples from normative statements.
- Avoid subjective interpretation.
- Use consistent governance terminology.
- Express rules in a clear and verifiable manner.

Governance documents should remain implementation-independent unless implementation is the document's explicit purpose.

---

# Terminology Rules

Official terminology shall remain consistent throughout the DevinaOS documentation ecosystem.

Each official concept should have one canonical name.

Synonyms should be avoided when an official term already exists.

Abbreviations shall be introduced only after their full name has been defined.

Terminology shall remain consistent across related documents to improve governance, searchability, AI interpretation, and long-term maintainability.

---

# Heading Rules

Documents shall use hierarchical Markdown headings.

Example:

```
# Document

## Section

### Subsection

#### Detail
```

Heading levels shall not be skipped.

Each heading should accurately represent the content contained within its section.

# Table Rules

Tables should be used when presenting:

- Definitions
- Comparisons
- Classifications
- Metadata
- Specifications
- Governance matrices
- Decision summaries

Tables shall include descriptive column headings.

Tables should remain concise, readable, and consistent throughout the documentation ecosystem.

---

# List Rules

Bullet lists should be used for unordered information.

Numbered lists should be used only when sequence or priority is important.

Nested lists should be minimized whenever practical to improve readability.

Lists should contain parallel grammatical structures whenever possible.

---

# Diagram Rules

Diagrams should be used only when they improve architectural understanding or clarify relationships that are difficult to explain using text alone.

Text-based diagrams shall remain readable in Markdown.

Visual diagrams may be maintained separately while remaining consistent with the authoritative document.

Diagrams shall complement documentation rather than replace written explanations.

---

# Example Rules

Examples should:

- Illustrate concepts clearly.
- Remain concise.
- Avoid unnecessary complexity.
- Clearly distinguish examples from normative content.
- Support understanding without introducing additional requirements.

Examples are informative and do not establish mandatory requirements unless explicitly stated.

---

# AI Readability

Documentation shall be structured to support AI-assisted interpretation, indexing, validation, and future automation.

Documents should:

- Use explicit headings.
- Use consistent terminology.
- Avoid hidden assumptions.
- Avoid duplicated definitions.
- Prefer structured information over free-form narrative.
- Define concepts before introducing abbreviations.
- Avoid circular references whenever possible.
- Maintain a single authoritative definition for each concept (Single Source of Truth).

---

# Writing Quality

Before approval, every official document should be reviewed for:

- Accuracy
- Completeness
- Consistency
- Grammar
- Terminology
- Structural compliance
- Governance compliance
- Cross-document consistency
- Reference validation
- Readability

Documents should be reviewed periodically to maintain long-term quality and consistency as the DevinaOS documentation ecosystem evolves.

---

# Compliance

Every official DevinaOS document shall comply with this standard.

Documents that do not conform to this writing standard shall be updated before receiving **Approved** status.

Compliance with this standard contributes to consistent communication, governance, AI interoperability, and long-term maintainability.
